# AutoManual-MM-RAG 中文简历与面试表述

> 本文只把已有代码、评测文件和真实 API 验证支持的内容写成“已完成”。
> Agentic GraphRAG / Multi-Agent 仍在独立分支开发，完成对照评测前不包装成既有成果。

## 一、简历可直接使用版

### AutoManual-MM-RAG｜汽车手册多模态检索与可追溯问答系统

**技术栈：** Python、MinerU、SQLite FTS5/BM25、NumPy、Pillow、Qwen3-VL、FastAPI、Gradio、Docker Compose

- 针对汽车手册篇幅长、车型内容易混淆、图片与参数表无法仅靠文本检索的问题，搭建从官方 PDF 下载、SHA-256 校验、MinerU 解析、结构化清洗到索引和评测的一体化流水线；处理 4 本 Ford 2026 车主手册，沉淀 30,131 个可追溯元素、12,236 个文本块、3,287 张图片和 516 个表格裁剪。
- 没有采用通用定长切块，而是围绕维修/使用场景设计证据结构：保留车型、年份、地区、章节、物理页码、相邻元素及原始资源路径，并单独保存操作步骤和 Warning/Caution；检索前执行车型元数据硬过滤，评测中跨车型证据泄漏为 0。
- 分别实现 BM25、Hash TF-IDF + 128 维随机 LSA、RRF、1,296 维传统图像特征及人工校验表格行检索，并用统一 Gold Set 做对照。26 个可回答文本问题中 BM25 Recall@10 达 0.9615，优于当前 Dense/RRF 基线，因此保留 BM25 为默认路径；12 个图片查询中图文融合 Recall@1 为 1.0000，23 条核验表格行的精确值覆盖率为 1.0000。
- 设计 Evidence Pack、有效引用校验、置信度/适用性门控和证据不足拒答机制，使 30 个文本问题的回答/拒答决策准确率达到 0.9667、无答案准确率达到 1.0000；接入法兰克福区域 Qwen3-VL 远程 API，完成一次真实图片问答闭环并引用正确物理页，同时交付 FastAPI、Gradio、可断点重跑流水线和 58 项自动化测试。

**项目链接：** <https://github.com/ZHANGzhile/AutoManual-MM-RAG>

## 二、篇幅较短时使用的三条版

- 独立落地汽车手册多模态 RAG：完成 4 本官方 Ford 手册的 MinerU 解析、结构化清洗和可追溯证据建模，构建 30K+ 元素、12K+ 文本块、3K+ 图片及 516 个表格的数据底座，并通过车型/年份/地区硬过滤消除跨车型证据混入。
- 实现并对照评测 BM25、LSA Dense、RRF、传统视觉和表格行检索；基于实验选择 BM25 作为当前文本默认方案（Recall@10 0.9615），图文融合 Recall@1 1.0000，回答/拒答决策准确率 0.9667，元数据违规为 0。
- 通过 Evidence Pack、页码引用、Warning/步骤保留和低置信拒答约束生成，完成 Qwen3-VL 真实图片问答验证；提供 FastAPI/Gradio、断点续跑全流程、机器可读评测报告和 58 项自动化测试。

## 三、一句话项目定位

这不是把 PDF 切块后直接交给大模型，而是针对汽车手册中“车型不能串、步骤不能乱、警告不能丢、参数不能猜、答案必须能回到原页”五个实际约束，完成了一套可重建、可评测、可拒答的多模态检索问答系统。

## 四、面试时的技术路线

### 1. 先解决数据是否可信

项目从 4 本厂商官方 PDF 开始，对下载文件做大小和 SHA-256 锁定。MinerU 单独运行在隔离环境中，避免其解析依赖与应用环境冲突；解析完成后通过成功标记支持断点恢复，避免重复处理大文件。

MinerU 输出没有直接进入向量库，而是先转换成统一元素 Schema。每条文本、图片或表格都带有稳定 ID、车型元数据、章节路径、物理 PDF 页码、坐标、相邻元素和源文件位置。严格导入会检查缺页、缺资源和异常引用，当前 30,131 个元素的导入异常数为 0。

### 2. 再按信息类型设计检索

- 文本：用 BM25 建立可解释基线，同时实现 Hash TF-IDF + 随机 LSA Dense 以及 RRF，避免在没有实验前预设“Dense 一定更好”。
- 图片：不在本地部署大模型，使用缩略图强度、边缘方向、颜色分布、投影和低频频谱组成确定性的 1,296 维特征，再与用户的文本提示做融合。
- 表格：对于扭矩、容量、充电参数等高风险数值，不让模型对图片自由猜测，而是从带源图哈希和适用条件的人工核验行中回答。

评测结果显示，当前 26 个文本问题上 BM25 Recall@10 为 0.9615，Dense 为 0.7692，RRF 为 0.8846。因此默认文本链路保留 BM25，Dense/RRF 作为实验基线。这一选择来自数据，而不是技术名词偏好。

### 3. 最后约束答案，而不只追求“能生成”

检索结果统一组装为 Evidence Pack，答案只能引用包内编号；车辆、年份、地区先做硬过滤，回答阶段再检查证据分数、问题覆盖度和适用性。操作类问题要求保留有序步骤及其附近警告，证据不足时返回明确拒答。

默认离线链路可以直接返回带页码的抽取式证据；远程 VLM 只负责在证据范围内组织答案。Qwen3-VL 的法兰克福 API 已完成一次付费端到端验证：系统对仪表符号检索出 5 条 Bronco 专属证据，回答安全带提醒指示灯，并引用到手册物理第 29 页。该结果只表述为集成验证，不夸大为生成质量基准。

### 4. 用工程闭环证明项目可以复现

完整流水线覆盖下载、解析、导入、切块、5 类索引、评测、审计和测试。已解析数据复用时，从导入到 58 项测试全部通过约需 33 秒。系统提供命令行、Gradio 三类查询界面和 FastAPI 的文本/图片/表格接口；大文件与密钥不进入 Git，Docker Compose 配置把索引和解析目录以只读方式挂载。本机已验证 Compose 配置可解析，但因当前终端没有 Docker CLI，尚未执行镜像构建，因此面试时不会把它表述为已验证的容器部署。

## 五、面试官追问时的回答要点

### 为什么不用一个向量数据库解决所有问题？

汽车手册的文本、图标和参数表有不同的错误模式。文本需要关键词和步骤匹配，图标需要视觉相似度，数值表需要精确字段和适用条件；统一塞进单一向量空间会降低可解释性，也不利于分别评测。当前对照实验还显示 BM25 比本地 Dense/RRF 更适合这组文本问题，所以没有为了架构复杂度强行替换。

### 为什么表格只做了 23 条人工核验行？

这是有意控制结论边界。扭矩、容量等数值答错的风险高，现阶段宁愿对 9 张代表性表格建立可审计的小型 Gold Set，也不把 516 张表格裁剪都宣称为可靠 OCR。简历中的 1.0000 精确值覆盖率仅指这 23 条核验行。

### 为什么还需要 VLM？

本地检索负责找对车型、页面和证据，VLM 负责理解用户上传的局部图片并在 Evidence Pack 内组织自然语言答案。这样远程模型可以替换，检索、引用和拒答规则不依赖某一家 API，也无需在本地部署模型。

### 项目目前最明显的不足是什么？

当前文本 Gold Set 为 30 个问题，视觉集为 12 个问题，表格行也是人工筛选的小规模集合；一次 Qwen 图片问答只能证明接口和完整链路可用，不能代表总体生成质量。下一步需要增加跨章节、多跳和冲突证据问题，并报告准确率、延迟、调用成本及失败案例。

## 六、正在开发：Agentic GraphRAG（暂不写成已完成）

当前独立分支正在把已有证据层扩展为领域图谱与受控 Agent 工作流，目标不是简单增加框架名，而是处理普通 Top-K 检索不擅长的跨章节问题，例如“某警告灯表示什么、适用于哪一车型、需要按什么顺序处理、相关警告和参数在哪一页”。

计划中的可交付证据包括：

- 从现有 Schema 确定性生成 Vehicle、Section、Component、Procedure、Step、Warning、Specification、Image、Table 和 Evidence Page 等节点，所有边可回溯到原始元素。
- Planner 只负责判断问题需要文本、视觉、表格或 1–2 跳图检索；Evidence Critic 检查覆盖度、车型一致性和引用完整性，最多触发一次有边界的重新检索。
- 建立 Baseline RAG、GraphRAG、Agentic GraphRAG 三组多跳问题对照，真实记录命中率、答案质量、延迟、API 成本和失败案例。

只有当上述代码、测试和对照结果完成后，简历才把这一段升级为“已实现”。届时优先写解决了哪些多跳失败，而不是只写使用了 GraphRAG、LangGraph 或 Multi-Agent。
